# ChronoLens 开发方案

方案日期：2026-10-13

状态：选题与设计方案，尚未实现

定位：MoonBit 实现的分布式日志时间约束诊断库，配套离线命令行工具与交互演示

## 1. 项目要解决什么问题

跨机器日志按时间戳排序，可能出现“接收早于发送”“下游服务提前开始处理”等现象。不同机器的时钟偏差、日志关联错误、时间戳记录位置和时钟跳变，都可能影响这种判断。

ChronoLens 输入结构化日志和明确的发送／接收关联，计算：

1. 在指定分析窗口内，是否存在一组固定时钟偏移，使日志满足设定的时间约束。
2. 各时钟相对于参考时钟的可行偏移范围。
3. 若约束无法同时满足，哪些日志及假设组成了可复核的矛盾证据。
4. 若关联或约束不足，哪些事件仍然无法确定先后关系。

目标用户是排查多服务调用、消息队列或多节点实验的开发者。主要产物是一份可以核对原始日志的诊断报告。

## 2. 选题价值与现有生态

### 2.1 差异化定位

项目重点是“偏移范围、冲突证据与不确定性”。核心算法可以作为 MoonBit 库供日志工具、实验平台和诊断系统调用。

Jaeger 已有根据调用关系调整时间戳的功能，其官方文档也说明：某些校正需要假设请求和响应的网络延迟相等。ChronoLens 可以将偏移的可行范围显式展示出来，使用户看到数据本身能支持多强的结论。

参考：[Jaeger Clock Skew Adjustment](https://www.jaegertracing.io/docs/2.22/deployment/configuration/#clock-skew-adjustment)。这说明问题和相关算法已有研究与工程实践；本项目的创新目标是补充 MoonBit 生态，并提供清晰的证据表达。

### 2.2 Mooncakes 查询记录

2026-10-13，本会话通过注册表执行：

```text

moon search 'clock alignment' --json --limit 20
moon search 'clock correction' --json --limit 20
```

返回结果中未发现直接处理“既有日志中的固定物理时钟偏移范围与矛盾证据”的同类项目。

| `Suquster/moonbit-pathfinding@0.2.0` 的 `src/dst` | 确定性仿真、时钟偏差等故障注入 | 对输入日志进行离线约束诊断 |

| 优先级 | 功能 | 首版交付内容 |

| P0 | 约束构建 | 固定时钟偏移模型、消息因果约束、可选偏移先验 |
| P0 | 求解 | 可行性判定、可行解、偏移上下界、无界状态 |
| P0 | 冲突解释 | 输出一个可验证的负环及对应日志、约束和假设 |
| P0 | 报告与 CLI | JSON、Markdown、稳定退出码、确定性输出 |
| P0 | 交互演示 | 内置样例、原始时间线、可行范围、冲突证据联动 |
| P1 | 实际数据适配 | 一个明确文档化的导出格式或日志转换示例 |

首版支持分析窗口内固定偏移。每次重启、时间跳变或时钟域变化，需要使用新的 `clock_id` 或分开分析。报告必须明确记录这一假设。

首版适合几十个时钟域、数千至数万条结构化事件。实际容量通过基准测试确定。

## 4. 用户使用流程

1. 导入日志，选择分析窗口。
2. 查看关联质量：成功配对的消息、缺失记录、重试歧义和非法字段。
3. 选择参考时钟，确认固定偏移和记录容差等假设。
4. 执行分析，查看每个约束连通分量的结果。
5. 点击异常或约束，跳转到关联的原始事件。
6. 导出报告，将证据附到故障复盘或实验记录中。

默认分析在本地进行。文件名和日志文本在报告中按文本转义，外部日志内容不得直接拼接为可执行 HTML。

## 5. 输入格式

### 5.1 事件模型

建议首版使用以下概念字段，具体 MoonBit 类型与公开 API 在实现前确定。

| 字段 | 要求 | 用途 |
| --- | --- | --- |
| `event_id` | 必填、全局唯一 | 定位证据和保证稳定输出 |
| `clock_id` | 必填 | 标识本次分析中的同一时钟域 |
| `trace_id` | 必填 | 隔离不同调用或实验 |
| `message_id` | 必填 | 标识一次有方向的消息传递 |
| `attempt` | 必填、非负整数 | 区分重试尝试 |
| `kind` | `send` 或 `receive` | 表示消息发送或接收 |
| `ts_us` | 必填、十进制整数字符串 | 原始时间戳，单位微秒 |
| `source` | 可选 | 来源文件及记录位置 |

时间戳以字符串保存，在核心中转为有溢出检查的 64 位整数。不同文件必须使用一致的时间尺度与单位；解析层不得自行猜测单位。

以下样例使用相对时间，四条事件组成一次请求和一次响应：

```jsonl
{"event_id":"a1","clock_id":"A","trace_id":"t1","message_id":"request-1","attempt":0,"kind":"send","ts_us":"1000000"}
{"event_id":"b1","clock_id":"B","trace_id":"t1","message_id":"request-1","attempt":0,"kind":"receive","ts_us":"900000"}
{"event_id":"b2","clock_id":"B","trace_id":"t1","message_id":"response-1","attempt":0,"kind":"send","ts_us":"940000"}
{"event_id":"a2","clock_id":"A","trace_id":"t1","message_id":"response-1","attempt":0,"kind":"receive","ts_us":"1100000"}
```

### 5.2 配对规则

配对键为 `(trace_id, message_id, attempt)`。一个键只有恰好一条发送和一条接收时，才生成消息约束。

- 缺失一端：记录为未配对事件，保留在报告中。
- 同一键存在多个发送或接收：记录为歧义，要求补充正确的消息标识。
- `event_id` 重复或字段非法：作为输入错误处理。
- 文件行顺序不代表事件因果顺序。
- 重试、广播和批量消息需要在上游转换为明确的一对一传递标识。

单纯的父子 Span 关系不直接转换为“父区间必须包住子区间”；任何适配器都需要先说明其事件语义。未来适配 OpenTelemetry 时，以其[官方数据与 API 规范](https://opentelemetry.io/docs/specs/otel/trace/api/)为依据。

## 6. 核心数学模型

### 6.1 偏移定义

对时钟域 `i` 定义偏移 `o_i`，模型时间为：

```text
T(event) = observed_timestamp(event) + o_i
```

这里的模型时间来自可行偏移，不能直接宣称为真实 UTC 时间。

选定参考时钟 `r`，令 `o_r = 0`。这是设置相对坐标；参考机器的时钟也可能有绝对误差。

### 6.2 消息约束

设发送时钟为 A，接收时钟为 B，观测时间分别为 `s_A` 和 `r_B`。默认要求：

```text
s_A + o_A <= r_B + o_B
o_A - o_B <= r_B - s_A
```

统一表示为差分约束：

```text
o_i - o_j <= c
```

对应图中的有向边为 `j -> i`，边权为 `c`。实现和测试中必须固定这一方向，避免上下界符号错误。

首版可提供显式的 `relation_tolerance_us`，默认值为 0。使用容差时：

```text
o_A - o_B <= r_B - s_A + relation_tolerance_us
```

容差表示允许每条关系有指定的记录误差，不是求得了每个事件的真实测量误差。配置值、受影响约束和最终假设必须进入报告。

用户提供的偏移先验同样转换为约束。例如 `L <= o_B - o_A <= U` 对应两条边。报告应标明其来自用户假设。

### 6.3 可行性与冲突证据

采用 Bellman–Ford 类算法判断差分约束是否存在可行解。全局检测可以通过超级源覆盖所有时钟；实际报告按约束图的弱连通分量组织。

- 无负环：该分量在当前假设下存在可行解。
- 存在负环：沿前驱边提取一个闭环，记录每条边的来源。
- 环上边权之和小于 0，说明这些约束不能同时成立。

首版输出的是一个冲突见证，不承诺它包含最少数量的事件。仅凭冲突，也不能确定是时钟跳变、错误关联还是日志记录方式导致；报告应给出可检查的原因候选。

一个分量冲突时，其他分量仍可独立分析。

### 6.4 偏移范围与无界状态

在可行分量内，设 `d(u,v)` 为约束图的最短路径距离。相对于参考时钟 r：

```text
upper(o_i) = d(r, i)
lower(o_i) = -d(i, r)
```

相应方向没有路径时，该侧无界。上界和下界可以通过原图与反向图各进行一次从参考点出发的最短路径计算得到。

不同分量缺少连接证据，各自选参考时钟并明确标记。分量之间不能直接画成一条具有确定先后的统一时间线。

各时钟的上下界是分别计算的；多个时钟的区间端点不一定能同时取到。前端展示一组代表偏移时，必须使用求解器给出的同一个可行解，不能随意拼接区间端点。

### 6.5 四事件示例

上面的 JSONL 转成毫秒后：

| 事件 | 观测时间 | 关系 |
| --- | ---: | --- |
| A 发送请求 | 1000 | 不晚于 B 接收请求 |
| B 接收请求 | 900 | 请求接收 |
| B 发送响应 | 940 | 不晚于 A 接收响应 |
| A 接收响应 | 1100 | 响应接收 |

以 A 为参考，容差为 0，可得：

```text
o_B >= 100 ms
o_B <= 160 ms
因此 o_B ∈ [100, 160] ms
```

取 100 ms 或 160 ms 都能解释这组消息关系。数据无法确定唯一偏移；界面应展示这一范围。

同一固定时钟域内，偏移会在时间差中抵消。例如 B 的两条记录间隔为 40 ms，A 的两条记录间隔为 100 ms。但要将它们解释为“处理耗时”或“往返耗时”，仍需正确的记录语义与关联。

## 7. 工程结构与公开能力

建议建立独立的 `chronolens/` 项目目录，以下为拟议分包：

```text
chronolens/
  model/           事件、约束、配置和报告类型
  input/           JSONL 解析、校验和资源限制
  correlate/       消息配对、歧义和未匹配记录
  constraints/     时间关系到差分约束的转换
  solver/          可行性、偏移区间、冲突见证
  report/          JSON、Markdown 和演示所需数据
  cmd/chronolens/  原生命令行入口
  demo/            交互演示与内置样例
  fixtures/        正常、缺失、歧义、无界与冲突样例
```

公开能力分成“端到端诊断”和“直接求解约束”两层，便于其他 MoonBit 项目接入自定义日志格式。公开类型和函数命名在实现阶段验证工具链后再确定。

核心求解器接收数据并返回结果，输入解析、文件操作和前端展示通过适配层连接。CLI 使用 native；浏览器演示采用经当前工具链验证的 JS 或 Wasm 后端。

### 7.1 性能与确定性

设时钟数为 V，原始约束数为 E。对同一有向时钟对，只保留最紧的上界用于求解，求解边数最多为 V²；原始约束保留在证据索引中。

最紧边要保存对应来源 ID；同权边按稳定规则选取代表，不能影响证据可追溯性。

首版设置事件数、时钟数、输入字节数、字段长度和运算预算上限。超限返回明确状态；所有时间加减和路径松弛都检查溢出。固定输入、配置和排序规则应产生相同报告。

性能验收目标：在记录硬件和构建方式的前提下，分析 1 万条事件、最多 64 个时钟域的标准样例，核心计算目标为秒级。该目标需要实际测量，当前不是已验证结果。

## 8. 报告与演示界面

报告至少包含：

- 版本、输入摘要、配置和全部模型假设。
- 输入错误、成功配对数、未配对事件和歧义记录。
- 每个分量的参考时钟、求解状态、偏移区间和一组可行偏移。
- 冲突见证：事件 ID、来源位置、约束方向、边权和负环权重和。
- 可行性、无界性、数据覆盖程度等独立信息。

界面建议采用“原始记录—时间线—证据”三个联动区域。点击时间线上的消息箭头，显示两条记录及对应不等式；点击冲突见证，高亮环上的消息。

状态文案必须区分：

| 状态 | 用户能得到的结论 |
| --- | --- |
| 当前模型可行 | 存在偏移能解释已构建的约束；不能说明日志完整或绝对时间正确 |
| 当前模型冲突 | 展示的约束无法同时满足，需要检查事件和假设 |
| 偏移无界或关联不足 | 当前证据不足以限定某侧偏移或跨分量先后 |
| 输入错误／资源超限 | 本次未完成有效分析，附具体原因 |

可行范围与代表时间线使用不同视觉标记。界面明确提示“代表时间线是一种可行解释”。

拟议 CLI 用法：

```text
chronolens analyze events.jsonl --reference A --json report.json --markdown report.md
chronolens explain report.json --conflict conflict-1
chronolens demo skew
```

以上命令是设计目标，尚不可执行。建议退出码约定为：0 分析完成且约束可行；1 至少一个分量冲突；2 输入或配置错误；3 资源超限。证据不足作为报告字段，并允许用户配置是否在 CI 中视为失败。

## 9. 样例与验证计划

| 样例 | 预期验收结果 |
| --- | --- |
| 同时钟正常消息 | 偏移为参考值，消息关系可行 |
| 四事件示例 | B 的偏移范围恰为 `[100,160] ms` |
| 单向消息 | 只得到一侧边界，另一侧明确无界 |
| 两个独立分量 | 分别求解，不能推断分量间先后 |
| 缺失接收事件 | 报告未配对，不自动补造接收记录 |
| 重复或重试歧义 | 标出关联歧义，相关键不生成约束 |
| 同时钟接收早于发送 | 在零容差下形成自环冲突 |
| 三个时钟构成负环 | 输出来源完整、可复算的负环 |
| 偏移先验与消息关系冲突 | 证据同时包含日志和先验假设 |
| 超大时间戳、畸形字段、超限输入 | 明确拒绝或返回受限状态 |

算法验证应包括：

1. 固定种子生成事件与真实偏移，确认生成偏移是一个可行解。
2. 检查每个返回可行解是否满足全部原始约束。
3. 检查每个冲突见证是否闭合，且权重和严格小于 0。
4. 在小图上使用独立的全对最短路参考实现，对照区间和可行性。
5. 打乱输入顺序后比较规范化报告。
6. 比较边压缩前后的求解结果。
7. 对核心进行跨后端结果比较，并验证演示界面的范围和见证与 JSON 一致。

真实样例建议从本地两服务的显式发送／接收记录开始，再按固定偏移修改各时钟域时间戳。注入偏移和原始日志一并保留，以便验证。真实网络运行与纯合成样例应在文档中明确标注。

## 11. 主要风险与控制方法

| 风险 | 控制方法 |
| --- | --- |
| 普通日志缺少明确消息关联 | 首版使用严格格式与转换示例，报告关联覆盖程度 |
| 时钟在窗口中漂移或跳变 | 缩小窗口或拆分时钟域，显式记录固定偏移假设 |
| 时间戳记录位置不符合发送／接收语义 | 在输入契约中明确采样位置，容差作为用户假设记录 |
| 一个可行解被误读为真实校准结果 | 始终同时展示区间、无界状态和参考时钟说明 |
| 不相关分量被强行合并 | 独立求解和展示分量，保留未知先后关系 |
| 冲突被误读为确定的根因 | 输出矛盾证据和检查候选，结论限定于当前模型 |
| 扩展真实日志适配拖慢开发 | 首版先固定 JSONL，选择一个明确来源作为后续适配 |
